## Week 1: Hardware & Platform

### 1.1 Windows HAL Implementation

**File:** `thermaliq-hal/src/windows.rs`

**Tasks:**
1. HWiNFO64 shared memory reader
   - Import `windows` crate: `Win32_System_Memory`, `Win32_Foundation`
   - Map `Global\HWiNFO_SENS_SM2` at startup (handle error gracefully if not running)
   - Parse `SensorStructure` header (offset 0, size ~540 bytes)
   - Parse `ReadingStructure` array (offset variable, count from header)
   - Filter sensors by type: `SENSOR_TYPE_TEMP` (4), `SENSOR_TYPE_FAN` (5), `SENSOR_TYPE_POWER` (3)
   - Refresh on 2000ms cadence
   - Return: `SensorReading`, `FanReading` types (already in `thermaliq-common`)

2. NVML GPU fan writes
   - Add `nvml-wrapper` crate to `Cargo.toml`
   - On first call, attempt NVIDIA driver init; log if driver < 520
   - Implement `set_fan_duty()` for GPU: `nvmlDeviceSetFanSpeed_v2(device_idx, speed_percent)`
   - Graceful fallback: log warning if NVIDIA not present or outdated

3. WMI fallback
   - Complete the stubbed WMI implementation
   - Use `Win32_TemperatureProbe`, `MSAcpi_ThermalZoneTemperature` for CPU temp
   - Use `Win32_Fan` for basic fan enumeration
   - Spawn WMI calls in `tokio::task::spawn_blocking` (COM not thread-safe)
   - Document sensor coverage gap vs HWiNFO64

**Acceptance Criteria:**
- [ ] `cargo build --target x86_64-pc-windows-msvc` succeeds
- [ ] Real HWiNFO64 shared memory reads return non-zero temps on Windows machine
- [ ] NVML fan write (0-100%) controls NVIDIA GPU fan speed
- [ ] WMI fallback works if HWiNFO64 is not running
- [ ] No panics on missing HWiNFO64; graceful degradation

## Week 3: AI & API

### 3.1 Multi-Provider AI Abstraction

**Files:**
- `thermaliq-common/src/ai.rs` (new) — trait definition
- `thermaliq-daemon/src/ai/mod.rs` (new) — provider implementations

**Tasks:**
1. Define `AIProvider` trait
   ```rust
   pub trait AIProvider: Send + Sync {
       async fn generate_profile(&self, prompt: &str, hardware: &HardwareSnapshot) -> Result<ProfileConfig>;
       async fn explain_intervention(&self, context: &InterventionContext) -> Result<String>;
   }
   ```

2. Implementations:
   - `AnthropicProvider` (use `anthropic` crate)
   - `OpenAIProvider` (use `openai` crate or HTTP client)
   - `GeminiProvider` (Google AI SDK)
   - `OllamaProvider` (HTTP to localhost:11434)
   - `OpenRouterProvider` (HTTP wrapper)

3. Provider selection in daemon startup
   - Read `config.toml`: `[ai] provider = "anthropic"` + `api_key = "..."`
   - Instantiate provider, validate API key on startup
   - If no key: log warning, disable AI features, continue

**Acceptance Criteria:**
- [ ] Each provider successfully generates a profile on valid API key
- [ ] Graceful fallback if key is missing or invalid
- [ ] Provider can be switched in Settings without restart

### 3.3 Safety Guardrails + Audit Log

**Files:**
- `thermaliq-daemon/src/poller.rs` — enforce guardrails
- `thermaliq-daemon/src/audit.rs` (new) — log all writes
- `thermaliq-common/src/config.rs` — guardrail config

**Requirements:**
1. Per-fan minimum duty% floor (e.g., never below 30%)
2. Global temp kill-switch (e.g., CPU > 95°C → all fans 100%)
3. Curve change cooldown (e.g., min 5s between changes)
4. Audit log table in `agent.db`:
   - `id, timestamp, fan_id, old_duty, new_duty, trigger (ai/manual/alert), reason_text`

**Acceptance Criteria:**
- [ ] Fan duty never goes below configured minimum
- [ ] Kill-switch fires when temp exceeds threshold
- [ ] Cooldown prevents oscillation
- [ ] Audit log records every write with timestamp + reason

### 3.5 MCP Server Implementation

**New crate:** `thermaliq-mcp/` (or standalone binary)

**Requirements:**
- Expose daemon REST API as MCP tools
- Tools:
  - `read_sensor(id: string) → temp/rpm`
  - `read_all_sensors() → HardwareSnapshot`
  - `set_fan_duty(fan_id: string, duty: int) → ok`
  - `switch_profile(name: string) → ok`
  - `get_agent_status() → running/paused`
  - `pause_agent()` / `resume_agent()`
  - `read_audit_log(limit: int) → [AuditEntry]`

**Implementation:**
- Thin wrapper around daemon HTTP API
- MCP protocol (JSON-RPC via stdio)
- Users can connect Claude Code, OpenClaw, etc.

**Acceptance Criteria:**
- [ ] Claude Code can read sensor data via MCP
- [ ] Claude Code can switch profiles via MCP
- [ ] MCP server auto-starts with daemon or runs as sidecar
